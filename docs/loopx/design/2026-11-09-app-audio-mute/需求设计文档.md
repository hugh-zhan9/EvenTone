# 应用静音详细合同

来源与决定：[概要 D-001](概要设计.md#D-001)、[概要 D-002](概要设计.md#D-002)。2026-11-09，实施合同。

## 接口与所有权

AudioApplications 读取 Core Audio process object list、PID 及输出活动（全部设备，见[概要 D-003](概要设计.md#D-003)）。可执行路径的 app 包是进程归属证据；无法归属的进程单列，不能合并不同应用。ApplicationMuteState 保存应用 id/name 与选择，生成目标 process object ID 集合，既不依赖 UserDefaults 也不处理 HAL。

AudioWorker 串行拥有该状态；改变选择时用临时副本，AudioRouter 接受成功后提交。列表轮询重新枚举进程并应用已选集合；UI 通过 AppModel generation 丢弃迟到结果。总开关关闭和失败清空状态，设备重建仅清理资源。

AudioRouter.start 接受 muted process IDs，在开启混音前建立原声静音并排除进程；更新时先扩展静音集合到旧新并集，再更新全局排除集合，最后缩减静音集合。避免恢复过程中重复原声；过渡可能短暂静音。空目标先销毁静音 input-only aggregate/IOProc，再销毁静音 tap。任何 HAL 错误由资源层立即停止所有资源并保留错误；即使 UI 丢弃过期响应，下一次轮询仍能读取错误，显式停止或成功重建后清除错误；销毁失败保留句柄供后续清理，不能丢失资源引用。

## 验收与检查

- AC-1 / TC-1：两个不同浏览器同时播放，静音 A 后 B 保持播放，恢复 A 后恢复声音；应用内多个音频子进程归为一行。
- AC-2 / TC-2：关闭总开关解除全部静音并清空选择；退出、重开不恢复静音选择。
- AC-3 / TC-3：进程消失、暂停和新 helper 出现能更新；已选应用空闲时仍可恢复。无音频输出显示空态。
- AC-4 / TC-4：HAL 创建、更新、清理失败明确报告，不显示成功；已有设备补偿、均衡、参考音与音频隐私合同保持。
- AC-5 / TC-5：设备变更重新应用当前会话选择；旧设备资源释放。

纯逻辑测试覆盖分组／选择／事务失败，HAL 及可听效果由实机验收。验证结果追加 docs/VERIFICATION.md。没有新增公开 RPC、数据库或持久设置。2026-11-10 用户已授权提交、合入 main 并推送；未请求另行发布版本。

## 2026-11-10 · 内置扬声器输入布局修正

来源：用户要求解决内置扬声器缓冲错误并验证三个输出。隔离副本的真实回调观测：tap metadata 起点为第 7 个通道，但禁用的 6 个物理输入通道未出现在 IOProc AudioBufferList 中；实际只有一个双通道、4096 字节的 tap 缓冲，输出同为双通道、4096 字节。原 inputStart=6 导致合法输入被拒绝；不是采样率或帧数不一致。

DSP 接受两种经配置约束的布局：实际总输入通道等于 tap 通道时使用起点 0；保留完整物理通道占位时要求前缀全部为 NULL 且与 metadata 起点完整对齐，再使用 metadata 起点。其余布局拒绝；数据指针、Float32 字节整除和输入输出帧数一致的保护继续保留。只在 et_enable_tap_input 已成功禁用全部物理输入的通路使用，不推测任意活跃缓冲属于 tap。

修复前新增回归 exit 133，原失败已被测试捕获。诊断只记录尺寸／通道／指针是否存在，不记录音频样本；临时探针留在忽略的 .build 目录，生产代码不带临时诊断。

2026-11-10：AC-1 扩展到任意应用，不设名称白名单；新增验证全部输出流的静音描述不绑定设备/stream，枚举包含不同输出设备的音频进程。微信真实视频需单独验收，电平归零不能代替原声消失的确认。
